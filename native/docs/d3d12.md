# D3D12 GPU output

The Windows SDK currently exposes D3D12 through the ordinary wgpu engine and
the CPU readback APIs. A foreign `ID3D12Resource` or shared NT fence cannot yet
be imported into `mt_render_export_gpu`; no host handle is accepted and no
external synchronization is modified.

The planned zero-copy path requires a same-adapter device, a shared texture (or
buffer fallback), and two shared `ID3D12Fence` objects. The library would wait on
the host-ready fence, write color/depth, signal the done fence, and retain the
resource until GPU retirement. Cross-adapter handles, mismatched formats,
multi-sample resources and untracked state are rejected before touching the
handles. Device removal makes the result unknown and requires rebuilding both
devices.

This remains unavailable because wgpu 30's DX12 HAL wrapping API only wraps a
resource created by the same HAL device and does not import an external fence.
Adding the path needs a dedicated HAL ownership layer plus D3D12 debug-layer
tests for pixel parity, fence reuse, resize, cancellation and destruction order.
