# D3D12 GPU output

## Usage

Call `mt_engine_d3d12_info` first and use the returned borrowed
`ID3D12Device*` to create the shared 2D texture and shared `ID3D12Fence`.
The resource and fence must therefore belong to the exact device used by the
engine; matching only the adapter is not sufficient, and cross-device import
is not supported. Import the texture with `mt_engine_import_d3d12_image`,
import the fence with `mt_engine_import_d3d12_timeline`, then call
`mt_render_export_gpu` and poll with `mt_engine_gpu_poll`. The Windows example
[`examples/d3d12-export-host.c`](../examples/d3d12-export-host.c) demonstrates
HDR and depth textures, fence reuse, bounded polling and readback comparison.

Set `WGPU_DX12_COMPILER=dxc` before SDK adapter enumeration or engine creation:
scene kernels can exceed FXC's limits. Distribute the SDK package's `lib/*.dll`
beside your executable, including `dxcompiler.dll` and `dxil.dll`.

The device and queue pointers returned by `mt_engine_d3d12_info` are borrowed:
do not call `Release` on them or destroy them. Keep them alive until engine
destruction has completed, and destroy the imported wrappers before closing
host handles or releasing host resources.

## Options

The output kind selects HDR, depth, center-depth or display conversion. HDR is
`R32G32B32A32_FLOAT` or `R16G16B16A16_FLOAT`; depth and center-depth are
`R32_FLOAT` or RGBA32F; display is `R8G8B8A8_UNORM`. A host-ready fence/value
may be supplied before the strictly increasing done fence/value. Reusing a
timeline requires a larger value; rejected calls do not touch either fence.

## Caveats

Only same-device, same-adapter, shared DEFAULT-heap, single-sample, one-mip UAV
textures are accepted; buffer import is not supported. The host state tracker must declare
the imported texture COMMON before the first export. The current tracker leaves
the texture COMMON after accepted export work; after a host readback transition
from COMMON to COPY_SOURCE, restore COMMON before signaling a ready value for a
later export. Keep resources, NT
handles and fences alive until the export is retired and destroy import
wrappers before closing them. `BUSY` and device removal require retry or device
recreation; a device-removed outcome is never reported as successful completion.
